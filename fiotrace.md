# `fiotrace.py` Documentation

## Overview

`fiotrace.py` is a per-job tracing wrapper used by `fiobatch.py` to collect block-layer trace data (`blktrace`, `blkparse`, `btt`) alongside `fio` workloads. While `fio` reports userspace submission-to-completion latencies (`slat`, `clat`, `lat`), it cannot separate time spent inside the Linux `blk-mq` layer and I/O scheduler (`Q2G`, `G2I`, `I2D`, or total pre-dispatch `Q2D = Q2C - D2C`) from time spent in the NVMe driver and device (`D2C`).

When `fiobatch.py` is invoked with `--trace --trace-script ../../../fiotrace/fiotrace.py`, it wraps each `fio` invocation inside `fiotrace.py` instead of calling `fio` directly:

```text
fiotrace.py <device> <label> <output_dir> [options] -- fio --output-format=terse -
```

`fiotrace.py` manages the lifecycle of `blktrace` and `fio`, isolates `fio`'s terse `stdout` stream so `fiobatch.py` can still parse the CSV row, aligns the trace analysis window with `fio`'s steady-state execution window (`ramp_time` through `fio` completion), snapshots the active scheduler and `queue/iosched/*` sysfs tunables, verifies trace integrity, and runs `blkparse` and `btt` to produce per-job latency summaries and `metadata.json`.

## CLI Usage and Arguments

```text
fiotrace.py DEVICE LABEL OUTPUT_DIR [options] -- FIO_COMMAND [ARGS...]
```

| Argument | Description |
| :--- | :--- |
| `device` | Target block device path (e.g., `/dev/nvme0n1`). |
| `label` | Subdirectory name created under `output_dir` for this run. |
| `output_dir` | Parent directory where per-job trace folders are stored. |
| `--startup-gap` | Seconds to wait between starting `blktrace` and launching `fio` (default: `5.0`). |
| `--ramp-time` | Explicit `ramp_time` to exclude (e.g., `10` or `10s`). If omitted, auto-detected from `ramp_time=` in the `fio` job. |
| `--buf-size-kb` | Per-CPU `blktrace` relay buffer size in KiB (`blktrace -b`). Useful for high-IOPS NVMe runs. |
| `--num-bufs` | Number of per-CPU `blktrace` relay subbuffers (`blktrace -n`). |
| `--fail-on-drop` | Fail the job (exit code `1`) if `blktrace` reports any dropped events in `blktrace.stdout`. |
| `--keep-raw` | Retain per-CPU `trace.blktrace.*` files after post-processing. By default, raw per-CPU files are unlinked when `fio` exits with `0`. |
| `--rm-trace-bin` | Remove `trace.bin` after `btt-summary.avg` is verified to save disk space across large sweeps. |
| `--no-snapshot` | Disable creating the reproducibility snapshot archive and SHA-256 manifest. |
| `--snapshot-dir` | Custom directory for the snapshot archive and manifest (defaults to `<run_dir>/snapshot`). |

## Per-Job Output Directory Layout

Each `<output_dir>/<label>/` directory contains:

- `metadata.json`: Structured JSON summary of the job (device, active scheduler, `iosched_params`, `startup_gap_sec`, `ramp_time_sec`, `fio_start_offset_sec`, `analysis_start_sec`, `analysis_end_sec`, `fio_runtime_sec`, `blktrace_total_events`, `blktrace_dropped_events`, `btt_counts`, `fio_rc`, `wrapper_rc`).
- `snapshot/`: Reproducibility snapshot produced by `create_snapshot()` (unless `--no-snapshot` is passed), containing:
  - `configs_<timestamp>.tar.gz`: Compressed archive of `fiotrace.py`, `fiobatch.py`, experiment `.json`/`.fio`/`.sh` files, `job.fio`, `scheduler.txt`, `iosched_params.json`, `metadata.json`, `btt-summary.avg`, and `resolved_config_<timestamp>.json`.
  - `resolved_config_<timestamp>.json`: Full resolved run configuration and metadata.
  - `manifest_<label>_<timestamp>.txt`: Key-value run summary followed by a `[checksums]` section with `sha256_file()` digests of every archived file.
- `job.fio`: Copy of the rendered `fio` job specification piped from `fiobatch.py`.
- `scheduler.txt`: Raw contents of `/sys/class/block/<dev>/queue/scheduler` captured immediately after `fio` finishes.
- `iosched_params.json`: Snapshot of `/sys/class/block/<dev>/queue/iosched/*` tunables when the scheduler has tunable parameters (`kyber`, `mq-deadline`, `bfq`).
- `fio.stdout`, `fio.stderr`, `fio.rc`: Raw `fio` output streams and exit code.
- `blktrace.stdout`, `blktrace.stderr`: `blktrace` summary output (including buffer drop counts) and errors.
- `postprocess.log`: Combined `stdout`/`stderr` from `blkparse` and `btt`.
- `trace.bin`: Merged binary trace produced by `blkparse` (filtered to `[analysis_start_sec, analysis_end_sec]` when `ramp_time > 0`, unless removed via `--rm-trace-bin`).
- `btt-summary.avg`: Aggregate stage latencies (`Q2Q`, `Q2G`, `G2I`, `I2D`, `D2C`, `Q2C`) consumed by `plot_btt.py`, `plot_block_layer_bars.py`, and `plot_scheduler_breakdown.py`.
- `btt-summary.dat`, `btt-summary_qhist.dat`, `btt-summary_dhist.dat`, `btt-summary.msg`, `sys_iops_fp.dat`, `sys_mbps_fp.dat`, `<maj>,<min>_iops_fp.dat`, `<maj>,<min>_mbps_fp.dat`: Per-job activity and histogram files generated by `btt`.
- `wrapper.rc`: Exit code of `fiotrace.py` (`0` on success).

## Execution Flow

### 1. Pre-flight Checks and Job Input Capture
1. Validates root privileges (`euid == 0`), verifies that `<device>` is a block device, and checks that `blktrace`, `blkparse`, `btt`, and `fio` are in `PATH`.
2. Creates `<output_dir>/<label>` with `exist_ok=False` so an existing run directory is never overwritten.
3. If `fio` is reading its job file from `stdin` (`-` in the `fio` command, which is how `fiobatch.py` passes the rendered template), `fiotrace.py` reads the piped job text into memory, writes a copy to `<run_dir>/job.fio` for provenance, and later feeds `<run_dir>/job.fio` to the `fio` child process on `stdin`.
4. Determines `ramp_time` (in seconds):
   - Uses `--ramp-time` if explicitly passed to `fiotrace.py`.
   - Otherwise inspects the `fio` command line, any `.fio` file arguments, and the piped `stdin` job text for `ramp_time=<duration>` (supporting unit suffixes such as `s`, `ms`, `us`, `m`, or unitless seconds).
   - Defaults to `0.0` if no `ramp_time` is present.

### 2. `blktrace` Startup Buffer (`--startup-gap`)
1. Starts `blktrace` in its own process group (`start_new_session=True`):
   ```text
   blktrace -d <device> -D <run_dir> -o trace [-b <buf_size_kb>] [-n <num_bufs>]
   ```
2. Waits `--startup-gap` seconds (default `5.0s`), polling `blktrace` every `100ms` to verify it stays alive while attaching to the kernel block tracepoints and allocating per-CPU relay buffers.

### 3. `fio` Execution, Scheduler Snapshot, and Dropped-Event Check
1. Launches `fio` in its own process group, redirecting its outputs to `<run_dir>/fio.stdout` and `<run_dir>/fio.stderr`.
2. Polls both `fio` and `blktrace` every `100ms`:
   - If `blktrace` exits before `fio` finishes, raises a `RuntimeError` immediately because the resulting trace would be truncated.
   - When `fio` exits, records the return code to `<run_dir>/fio.rc`.
3. Immediately snapshots `/sys/class/block/<dev>/queue/scheduler` to `<run_dir>/scheduler.txt`, parses the bracketed active scheduler (such as `[kyber]` or `[mq-deadline]`), and reads all scalar tunable files in `/sys/class/block/<dev>/queue/iosched/` into `<run_dir>/iosched_params.json` and `metadata.json`. Capturing `queue/iosched/*` right after `fio` finishes guarantees that the scheduler specified by `fio`'s `ioscheduler=` option is active when its parameters (such as `read_lat_nsec` and `write_lat_nsec` for `kyber`) are read.
4. Stops `blktrace` cleanly by sending `SIGINT` to its process group (falling back to `SIGTERM` and `SIGKILL` only if it fails to exit within the timeout) so all per-CPU kernel relay buffers flush to `trace.blktrace.<cpu>`.
5. Parses `<run_dir>/blktrace.stdout` for `Total: <N> events (dropped <D>)`. If `dropped > 0`, logs a warning (or raises a `RuntimeError` if `--fail-on-drop` is set) and records both counts in `metadata.json`.
6. Copies `<run_dir>/fio.stdout` to `fiotrace.py`'s `stdout` (and `fio.stderr` to `stderr`). All diagnostic logging from `fiotrace.py` itself goes to `stderr` so `fiobatch.py` receives only the raw terse CSV output from `fio` on `stdout`.

## Handling `startup-gap`, `ramp_time`, and Post-`fio` Window Alignment

When `ramp_time` is configured in `fio` (for example, `ramp_time=10s` with `number_ios=100000`), `fio` issues I/Os for 10 seconds to warm up the device and scheduler state, resets its internal statistics at the 10-second mark, and then issues 100,000 measured I/Os. `blktrace`, however, records all block events from the moment it starts until it receives `SIGINT`.

Excluding warm-up and tail activity requires accounting for how `blkparse` and `btt` define trace time `t = 0.0`:

### Why Trace Time `t = 0.0` Is Not `blktrace` Start Time
In `blktrace`, the kernel stamps each `struct blk_io_trace` record with `ktime_get_ns()`. When `blkparse` merges the per-CPU `trace.blktrace.<cpu>` files into `trace.bin`, it finds `genesis_time`, which is the earliest non-notify event timestamp across all CPUs, and subtracts `genesis_time` from every event.

- Case A: Device is completely idle during `--startup-gap` (typical case).
  No block events occur during the 5-second `--startup-gap`. The first block event recorded by `blktrace` is `fio`'s very first `Q` event at the beginning of `ramp_time`. `blkparse` sets `t = 0.0` to that first `fio` `Q` event. Thus, in `blkparse` and `btt` coordinates, the 10-second `ramp_time` spans `[0.0s, 10.0s]`, and the measured workload begins at `t = 10.0s` (not `15.0s`).
  *(If you passed `-t 15.0` to `btt` in this case, `btt` would skip the 10s `ramp_time` plus the first 5s of the measured workload, which would discard the entire `number_ios=100000` run.)*

- Case B: A stray background I/O occurs during `--startup-gap`.
  If a background kernel thread (such as an XFS worker) issues an I/O at wall-clock `T = 1.5s` during the 5-second `--startup-gap`, `blkparse` sets `t = 0.0` to that stray event. When `fio` launches at `T = 5.0s`, `fio`'s first `Q` event appears at trace time `t = 3.5s`, and the 10-second `ramp_time` ends at `t = 13.5s`.

### How `find_fio_window_bounds_sec()` Computes Exact Start and End Bounds
Before running `blkparse`, `fiotrace.py` scans the binary 48-byte `struct blk_io_trace` headers (`<linux/blktrace_api.h>`) across `trace.blktrace.*` in two passes:
1. Pass 1: Finds `genesis_ns` (the minimum `time` of the first non-notify event on each CPU, where `(action & BLK_TC_NOTIFY) == 0`) and collects all `fio` PIDs from `BLK_TN_PROCESS` notification records whose payload name starts with `"fio"`.
2. Pass 2: Scans `Q` events (`(action & 0xffff) == __BLK_TA_QUEUE`) across all CPUs to find:
   - `first_fio_q_ns`: earliest `Q` event issued by a `fio` PID.
   - `last_fio_q_ns`: latest `Q` event issued by a `fio` PID.
   - Any stray non-`fio` `Q` events occurring after `last_fio_q_ns` (during the `<= 100ms` polling interval before `blktrace` receives `SIGINT`). Note that `C` (completion) events are intentionally not filtered by PID because NVMe interrupt completions execute in interrupt/kernel context (`pid == 0`) rather than under `fio`'s PID.

From these timestamps, `fiotrace.py` computes:

```text
fio_start_offset = (first_fio_q_ns - genesis_ns) / 1e9
analysis_start_sec = fio_start_offset + ramp_time_sec
analysis_end_sec = (earliest_post_fio_stray_q_ns - 1 - genesis_ns) / 1e9  (or unbounded if none)
```

### Filtering in `blkparse` and `btt`
When `ramp_time_sec > 0` (or when a post-`fio` stray `Q` event is detected), `fiotrace.py` applies the window bounds to both tools, running both with `cwd=run_dir`:
1. **`blkparse -i trace -d trace.bin -O -w <analysis_start_sec>:<analysis_end_sec>`**
   Drops all events outside the analysis window when building `trace.bin` (while still preserving `BLK_TN_PROCESS` process-name mappings). This keeps `trace.bin` small (~20 MB for 100,000 I/Os instead of ~450 MB if 10 seconds of `iodepth=128` ramp I/Os were retained).
2. **`btt -i trace.bin -o btt-summary -t <analysis_start_sec> -T <analysis_end_sec>`**
   Instructs `btt` to only analyze I/Os within `[analysis_start_sec, analysis_end_sec]`. Running `btt` with `cwd=run_dir` also keeps `btt`'s auxiliary `sys_iops_fp.dat`, `sys_mbps_fp.dat`, `<maj>,<min>_iops_fp.dat`, and `<maj>,<min>_mbps_fp.dat` files inside `<run_dir>/` instead of polluting the parent experiment directory.
   *(Implementation note: `btt` has an upstream quirk where passing `-t` without `-T` leaves its internal `t_aend` bound at `0.0`, causing `btt` to reject all events. Always supplying `-T` alongside `-t` avoids this bug.)*
3. **`btt-summary.avg` Validation:**
   After `btt` finishes, `parse_btt_counts()` parses the `All Devices` table in `btt-summary.avg`, records the sample counts (`Q2G`, `G2I`, `I2D`, `D2C`, `Q2C`) in `metadata.json`, and logs a warning if `count(Q2C) != count(D2C)`.
